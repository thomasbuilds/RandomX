## 1. Bottom line

No consensus-breaking defect was found in RandomX v2. The reference interpreter implements `doc/specs.md`
exactly for v1 and v2. The x86-64, ARM64 and RISC-V JIT compilers were verified bit-exact against the
interpreter with instruction-level decoding plus program-level differential execution (x86: 311,040
encodings and more than 29,000 program comparisons; ARM64: 660 program comparisons; RISC-V: 204 comparisons of
68 programs, including crafted edge cases, for the scalar JIT and for the vector JIT at each of VLEN 128,
256 and 512). The SuperscalarHash/Argon2/Blake2
pipeline was verified against the specification and independent models (reciprocals exhaustively over all
2^32 divisors, Argon2 reference/SSSE3/AVX2 byte-identical, RFC test vectors, 1.1 million Dataset items
through three independent executors). Dynamic testing on x86 produced about 10,000 cross-flavour hashes
(interpreter/JIT, soft/hard AES, secure, light/full, batch API, version switching, re-keying) with zero
mismatches, also under ASan, UBSan and TSan. Emulated runs on aarch64, riscv64 (scalar, vector at VLEN
128/256/512/1024, with and without Zvkned, Zba/Zbb), s390x, big-endian ppc64 (portable, VSX, VSX+crypto)
and ppc64le pass the test suite and compute the same hashes as x86.

Three real, pre-existing (v1-era) defects were found and fixed. None of them changes a hash on a
correctly behaving system, so no test vector changes:

1. **ARM64 light-mode JIT (Medium).** The freshly computed Dataset item was read from stack memory below
   SP after the 96-byte frame had been released. AArch64 has no red zone, so a signal frame delivered in
   that window corrupts the item and yields a wrong hash in light (verification) mode. Latent on Linux
   (the kernel's signal frame leaves that area untouched), live on macOS and FreeBSD arm64. A proof of
   concept with an asynchronous signal handler produced 3-6 wrong hashes out of 6 before the fix and 0 after.
2. **RISC-V vector JIT, misaligned light-mode data (Medium).** The two 8-byte words holding the Dataset
   initialisation entry point and the Dataset offset followed a 2-byte `ret` without alignment and were
   read with two misaligned `ld` per iteration (32,768 per hash). RISC-V does not guarantee misaligned
   scalar loads: trap-and-emulate slowdown on Linux, SIGBUS on systems without emulation. Same class as
   the earlier fixes #356/#357; invisible under qemu, which permits misaligned loads.
3. **RISC-V vector JIT, IMUL_RCP literal addressing (Low in practice).** The literal load for the 257th
   and later IMUL_RCP instruction of a program overflowed the 12-bit `ld` immediate (the pool grew from
   256 to 384 entries with v2 but the read side was not updated), producing a wrong hash for such programs.
   Unreachable with generated programs (the expected count is 12 per program; probability of 257 or more is
   about 2^-944), so no consensus exposure; fixed because non-default configurations and crafted inputs hit it.

Everything else is Low or Informational: robustness problems that crash or misbehave on unusual hosts
(SIGILL instead of a NULL return when hardware AES is forced on a CPU without it; AVX2 Argon2 selected on a
system whose OS has not enabled the AVX state; a 2 MiB large-page leak on every release; a machine created
from a never-initialised cache in release builds), hygiene (uninitialised NEON temporaries and JIT flag
members, a NULL-pointer memcpy, tool bugs), specification and documentation gaps (the v2 AES register mix
was not defined precisely enough to reimplement, `RANDOMX_FLAG_V2` was undocumented) and test-coverage
gaps (no test exercised JIT with hardware AES, secure JIT on x86, the full Dataset, or the v2 CFROUND
gate). All of these are fixed or documented on the branch.

Round 2 (concurrency, fuzzing, API edge inputs and static analysis, non-default configurations, 32-bit and
reduced-feature builds) is reported in section 7; it found no defect affecting the default configuration on
64-bit platforms and fixed two configuration-only defects and several robustness items.

### 2.3 Emulation artefact (not a RandomX defect)

The ppc64le build with `-mcpu=power8` dies with SIGILL under qemu's POWER8 model, while the same binary
passes everything under `-cpu power9`. The faulting block contains `xxspltib`/`stxv` (ISA 3.0) at an
address outside the executable: the Ubuntu 24.04 cross toolchain is configured `--with-cpu=power9` and its
libstdc++ and libc contain ISA 3.0 instructions (166 `xxspltib` in libstdc++). A C++ hello-world dies the
same way; the RandomX objects contain no ISA 3.0 instruction.

One aarch64 differential log (`agentJ/runs/rxdiff-aarch64-default.txt`) reports a single "mismatch": the process was
killed (SIGTERM) while writing its last line, which is a truncated hash (62 hex digits). The five re-runs of the same
matrix (`rxdiff-aarch64-k0b` to `k4`) match the x86 reference on every flavour.

## 3. What was verified as correct (and how)

**Interpreter and portable code.** Every instruction handler, the CFROUND v2 gate, the v2 AES register mix
(4 pairs of encrypt/decrypt rounds with keys e0..e3), the prefetch-two-ahead memory registers, address
masks, rounding-mode mapping and the final hash were checked line by line against `doc/specs.md`. Soft AES
equals AES-NI and FIPS-197 on 2 million random and structured inputs; the AES generator/hash constants were
re-derived from Blake2b; the 3200-byte program-prefix property and `hashAndFill == hash o fill` hold.
Generic (no-intrinsics) and fake big-endian builds pass. UBSan, ASan, TSan and clang `-fsanitize=undefined
-fsanitize-trap` are clean; CFROUND verified on 200,000 random inputs against a reference.

**x86-64 JIT.** All 311,040 (instruction, src, dst, mod, imm-class) encodings compared against the
interpreter semantics; more than 29,000 program-level differential comparisons (register file and
scratchpad) and 12 end-to-end machine variants with a real Dataset: 0 mismatches. Code-size bound margin
2,553 bytes; W^X transitions bracket every write; `.S` and `.asm` templates are byte-equivalent;
`configuration.asm` matches `configuration.h`.

**ARM64 JIT.** Every emitted word hand-decoded and cross-checked with objdump; AES mix verified as
`aese/aesmc/eor` and `aesd/aesimc/eor` (x86 AESENC/AESDEC semantics, zero key register written by the
JIT); CFROUND FPCR mapping; buffer bound 18,432 vs. worst case 15,360 bytes; branch ranges; cache-flush
ranges cover every patched word. 660 program comparisons and 4 Dataset-initialisation range checks against the
interpreter: 0 mismatches. Test suite passes under qemu (default and secure builds, static and shared library).

**RISC-V JIT (scalar and vector).** Every opcode constant and field placement decoded against the ISA
(RV64GC, Zba, Zbb, Zicbop, V 1.0, Zvkb, Zvkned) and against the interpreter; all template patch offsets
(2-byte vs. 4-byte slots) verified on assembled objects; relocation listings show no PC-relative reference
leaving a copied region; W^X and instruction-cache flushes cover all generated code. Differential harness:
scalar 204/204 and vector 204/204 (after C-F2) at VLEN 128/256/512 over 17 program families with crafted
edge cases (every immediate class, rotations by 0/31/32/33/63/64, all CFROUND gate values, all ISTORE
modes, every CBRANCH branch form, 384 x IMUL_RCP). Hardware-AES harness (soft interpreter vs. Zvkned
interpreter vs. Zvkned vector JIT, full and light): 18/18 at VLEN 256 and 512. Official suite passes at
VLEN 128/256/512/1024 with and without Zvkned, with GCC 13 (intrinsics shimmed) and GCC 14. The audit's RISC-V
builds used GCC 13 with an inline-assembly shim for the two Zvkned intrinsics; on 2026-10-22 the final tree was
rebuilt with GCC 14.2 and no shim: the suite passes on the scalar JIT, at VLEN 128, and with Zvkned at VLEN 256, 512
and 1024, and the differential harness gives 204/204 on the scalar JIT and at VLEN 128, 256 and 512.

**SuperscalarHash, Argon2, Blake2, reciprocal, Dataset.** `randomx_reciprocal` C == x86 asm == spec model
for all 4,294,967,263 divisors; Argon2 reference == SSSE3 == AVX2 on the full 256 MiB cache for 6 keys and
the RFC 9106 vector; BLAKE2b RFC vectors plus 3,000 random inputs against hashlib; Blake2Generator
against a model over 6 million calls; superscalar generator rules checked over 80,000 programs (0
violations, size <= 485 < 512); `executeSuperscalar` == independent executor == x86 JIT on 1.1 million
items; Dataset items for odd start/count combinations (fewer than 4, not a multiple of 4, near the end)
match per-item initialisation; interpreter and JIT Dataset initialisation are memcmp-equal.

**v2 design.** The AES register mix is a bijection; the CFROUND gate bits are disjoint from the rounding
bits; the prefetch recurrence is as designed; the 3200-byte prefix property holds; the cost claims in
`design_v2.md` are numerically consistent.

**Fix commits #340-#363.** Each was re-derived (sizes, offsets, symbol visibility, misaligned-store
removal, SIGILL probing, execute-only template placement); the big-endian ppc64 VSX+crypto run validates
#345/#357 and the shared-library a64 run validates #354/#363. The fork is identical to upstream `a901d5b`.

## 5. Residual risks and recommendations

1. **Run on real hardware before release.** Three things cannot be observed in this environment: the ARM64
   fix and the SECURE/W^X paths on macOS arm64 and FreeBSD arm64 (B-1 is live there), misaligned-access

## 7. Round 2: beyond the default configuration and the 64-bit targets

After the first round the maintainer asked for everything to be audited, not only v2. Round 2 added five
tracks: concurrency under ThreadSanitizer and AddressSanitizer; a coverage-guided fuzz campaign plus a
MemorySanitizer attempt; an API edge-input sweep with static analysis and a compiler-flag review; the
library under non-default `configuration.h` parameters; and 32-bit x86 (x87 and SSE2 math), armv7 and
x86-64 CPUs without AES-NI, SSSE3 or AVX2. The tree audited was the round-1 result (`2c1f5ec`).

### 7.1 Bottom line

No defect was found that affects Monero's configuration on a 64-bit platform. Every 32-bit and
reduced-feature build computes the same hashes as the 64-bit reference, the public API holds its documented
contract on every edge input tried except one out-of-range `randomx_init_dataset` call that wrote past the Dataset
(N-B, Low, fixed), static analysis and the compiler-flag review found no determinism
hazard (no fused multiply-add is ever emitted on the hash path, the rounding-mode write is never crossed by
a floating-point operation), and the alternative configurations (five valid configurations and a 2 GiB extra
Dataset) agree between interpreter and JIT, soft
and hardware AES, light and full mode, and across x86-64, ARM64 and RISC-V.

Two configuration-only defects were found and fixed: the RISC-V vector JIT could overflow its fixed-size
SuperscalarHash buffers for larger `RANDOMX_SUPERSCALAR_LATENCY`/`RANDOMX_CACHE_ACCESSES` settings (memory
corruption and a crash; with the default configuration at most 290 of the 512 literal slots were seen over 20,000
keys), and the ARM64
JIT silently truncated the light-mode Dataset offset for `RANDOMX_DATASET_EXTRA_SIZE` of 1 GiB or more
(wrong hashes). Both are now bounded by the parameters or rejected at compile time. Two Low findings on
32-bit x86 were fixed as well (CPU detection was x86-64 only, so an AES-enabled 32-bit build crashed on a
CPU without AES-NI; the Dataset cannot be allocated in a 32-bit process, now documented).

The concurrency track found no new defect: 8,793 worker-thread hashes across shared caches, shared
Datasets, Monero-style epoch switching, concurrent machine creation and destruction, the batch API and
multi-threaded Dataset initialisation all matched single-threaded references, with no AddressSanitizer or
UndefinedBehaviorSanitizer report. The only ThreadSanitizer report was the known benign race on the static
hardware-AES probe, which is now removed; the public header gained a thread-safety paragraph.

The fuzz campaign found no defect either: 14,959 coverage-guided program injections, each a full
2,048-iteration program compared register by register and over the whole scratchpad between the interpreter
and the x86-64 JIT in soft-AES, hardware-AES and secure flavours, plus 3,657 full-mode programs, 7,272
further differential comparisons on ARM64 and RISC-V under qemu, about 2.4 million executions of the AES,
BLAKE2b, SuperscalarHash and public-API targets, and a MemorySanitizer run, with zero mismatches and zero
sanitizer reports attributable to the library. Line coverage of the interpreter and the x86-64 JIT reached
93 to 98 percent, and every uncovered line is unreachable by construction (unreachable switch arms, the
disabled NOP instruction, error paths).

### 7.3 Verified as correct (and how)

**32-bit and reduced-feature builds (agent P).** 32-bit x87 (no SSE2) and 32-bit SSE2 builds pass the
suite (101 of 124 tests, the rest JIT or x86-64 only), reproduce the benchmark results and match the x86-64
reference on all 186 differential hashes each; 6,000 injected floating-point-heavy programs per build are
bit-identical to x86-64, and 440,145 single-operation comparisons in every rounding mode differ only when
subnormal operands are injected, which the no-denormal invariant excludes (this is the one platform where
the invariant is bit-visible, and it held). Disassembly confirmed one x87 operation per lane between a
load and a store at 53-bit precision, so no extended exponent survives across VM instructions. armv7 with
VFPv3-D16 and with NEON-VFPv4 under qemu pass the suite and match the reference (pure VFP double
arithmetic, no fused multiply-add, no NEON floating point). x86-64 under qemu `qemu64`, `Nehalem`,
`Westmere`, `Haswell,-xsave`, `Haswell` and `max` reports the expected flags, passes the suite, and the
benchmark matches on every available flavour; `-march=native` on the AVX2+FMA host emits no FMA and is
byte-identical to the default build on 3,000 programs.

**Non-default configurations (agent O).** Five configurations (fork-like Argon2 and cache changes,
512-instruction programs, skewed frequencies, small memory, longer SuperscalarHash) plus a 2 GiB extra
Dataset and six deliberately invalid settings. A host-side model of the generated SuperscalarHash code was
validated against runtime traces. For every configuration that builds, interpreter and JIT, soft and
hardware AES, v1 and v2, light and full mode, batch API, commitment and version switching agree on x86
(552 hash lines, 90 Dataset slices against per-item interpreter initialisation), and ARM64 and RISC-V
(scalar and vector) under qemu match x86 line by line, including a clang ASan+UBSan run.

**API edge inputs, static analysis and flags (agent N's harness, run by the lead after the agent was
stopped by an API safeguard).** 586 light cases (flag sweeps 0-255 for every allocator, key sizes 0 to
1 MiB, input sizes 0 to 16 MiB, unaligned and overlapping buffers, every batch-API ordering, 1,000 cache
switches, accessors) and about 990 heavy cases with a Dataset (of 1,053 planned): all in-contract cases pass, the
20 abnormal exits are documented misuse, and one out-of-range call wrote past the Dataset (N-B, fixed). cppcheck (637 messages) and clang-tidy (156) triaged: no true positive in the
library. gcc and clang `-O3 -march=haswell` and clang LTO: zero fused multiply-add instructions in any
hash-path object; the rounding-mode write is followed directly by a return or jump in both compilers; no
`-ffast-math`, `-ffp-contract` or `/fp:fast` anywhere; MSVC projects use the default precise model with
`/arch:AVX2` only for the AVX2 Argon2 file.

**Concurrency (agent L).** Three builds (gcc ThreadSanitizer, clang ASan+UBSan+LSan, plain) and 38 runs of
a nine-scenario harness over the documented contract: 8 mixed machines (interpreter, JIT, JIT+SECURE, soft
and hardware AES, v1 and v2) on one cache; a Dataset initialised by 4 threads and shared by 8 full-mode
machines; cache and Dataset epoch switching with per-round references; 1,200 machine create/destroy cycles
with W^X toggling and huge-page fallback while other threads hash; the batch API; SECURE light JIT machines
on a JIT cache (a `PROT_NONE` experiment proved they never execute the cache's own JIT buffer);
multi-threaded Dataset initialisation with unequal and 1-to-7-item tail ranges byte-identical to the
single-threaded result; startup races with 8 to 16 threads; 176,000 concurrent commitment calls. Zero
mismatches, zero ASan/UBSan/LSan reports, and only the probe race under ThreadSanitizer (now gone).

**Fuzzing (agent M).** A libFuzzer harness (clang 18, ASan+UBSan) injects a program, the entropy words,
the initial register values and a scratchpad seed, runs the interpreter and one JIT flavour for the full
2,048 iterations and compares the register file, a hash of the 2 MiB scratchpad, the rounding mode left
behind and the final hash. A self-test with a deliberately corrupted JIT register proved the oracle. Seeds
came from the crafted families of rounds 1 (every immediate class, rotations, CFROUND gates, ISTORE modes,
CBRANCH forms, 384 x IMUL_RCP). Results: light mode 14,959 executions (868 corpus units, 546 edges, 13,476
features), full mode with a sparse Dataset 3,657 executions, zero artifacts; RISC-V scalar and vector JIT
4 x 1,156 comparisons and ARM64 2,648 checks under qemu, zero failures; soft AES vs AES-NI 240,357
executions, BLAKE2b against an independent RFC 7693 implementation 2,125,165, SuperscalarHash generator and
executor invariants 65,017, public API including Argon2 AVX2 vs reference on key lengths 0 to 200: zero
reports; MemorySanitizer 273 executions, zero reports.
